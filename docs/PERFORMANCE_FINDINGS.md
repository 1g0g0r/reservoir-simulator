# Оптимизация солвера: замеры, варианты и что подключено

Все числа сняты на этой машине (8 физических ядер, Python 3.12, numba 0.65.1) на штатной постановке
`start.py`: сетка 25x25, две скважины по диагонали, `init_Wp = 0`. Профили «до» и «после» сняты при
одинаковых константах (`Twater = 70`), чтобы сравнение было корректным.

## Итог

Полный расчет до предельной обводненности (39717 шагов, 1986 суток, КИН 0.517):

| | было | стало |
|---|---:|---:|
| компиляция при запуске | 25.5 c | 4.9 c |
| счет | ~4.4 мин (оценка) | 11.9 c (замер) |

Прежний код до конца не гонялся, поэтому 4.4 минуты - это 39717 шагов на замеренные 6.58 мс/шаг.
Оценка честная: число шагов от оптимизаций не зависит, шаг весь расчет упирается в `dt_max`.

Тот же грид (25x25) сегодня, на Intel i5-4460 (4 ядра): компиляция 4.2 с (тёплый кеш), медиана шага
`bench.py` - 347.7 мкс, полный прогон до предельной обводнённости - 21 с (компиляция отдельно, 2.9 с).

## Найденные узкие места, по убыванию вклада

### 1. `psutil.virtual_memory()` на каждом шаге - 3.5 мс, 53% всего расчета

`_logging_solution` вызывался каждый шаг и через `_logging_resources` дергал
`psutil.virtual_memory()`. На Windows этот вызов стоит **3504 мкс** - больше, чем весь остальной
шаг. Для сравнения:

| вызов | мкс |
|---|---:|
| `psutil.virtual_memory()` | 3504.2 |
| `psutil.Process().memory_info()` | 3.4 |
| `logger.info`, одна строка | 24.0 |
| `p.min()` + `p.max()` | 3.9 |

Сделано - см. `CLAUDE.md`, раздел «Логирование».

### 2. Вложенный список на каждой ячейке - 92% времени сборки матрицы

В `_fill_matrix_and_rhs` и в `flows_in_cells` на каждой ячейке создавался
`arr = [[i+1, j, hx, hy*h], [i-1, j, ...], ...]`. В numba это список списков в куче, то есть
625 аллокаций на каждую из двух функций на каждом шаге.

| вариант сборки матрицы | мкс |
|---|---:|
| как было, со списком | 388.3 |
| то же, но смещения в константных массивах модуля | 32.4 |
| сборка сразу в три диагонали, параллельно, по предвычисленным подвижностям | 20.3 |
| + предвычисление подвижностей `calc_mobility` | 26.5 |

Побочно этот список делал индексы `float64` - в исходном коде за ним стояло `int(i1), int(j1)`.

### 3. Подвижности пересчитывались по 8 раз на ячейку

`mid_Ko_Kw`, `up_ko`, `up_kw` каждый раз считали `k*pf/mu` для обеих ячеек грани, то есть по
8 вычислений `pf_o`/`pf_w` на ячейку в сборке матрицы и столько же в перетоках. Вынесено в
`calc_mobility` (CLAUDE.md, раздел «Numba, а не ООП») - 6.6 мкс на шаг, параллельно, один раз.

## Что не делал

- **Замена `WellStruct` на плоские массивы.** Убрала бы последние ~2.5 c компиляции и накладные
  расходы отраженного списка. Противоречит намеренному решению держать скважины jitclass'ом;
  отдельная задача.
- **Алгебраический многосеточный метод (pyamg).** На 625 неизвестных избыточен. Станет интересен
  при переходе на сетки от 100x100, где ленточный Холецкий деградирует как O(Nx^3 * Ny).
- **Неявная схема по насыщенности.** Убрала бы ограничение CFL и сократила число шагов на порядок,
  но это смена численной схемы, а не оптимизация (см. `NUMERICS_FINDINGS.md`).
- **`fastmath=True`.** В прототипах давал единицы процентов; в проекте он всюду закомментирован,
  и я не стал менять это решение в обход автора.
- **Кеширование сохраняемых слоев в памяти** (`TODO` в `upd_time_step`): запись идет раз в
  `sol_time_step`, на фоне 0.27 мс/шаг это не узкое место.

## Где на самом деле было время

Стадии в сумме давали 682 мкс при шаге 1835 мкс - 63% не покрывалось. Разгадка не в Python-обвязке
(`_check_pressure` 10.6 мкс, `dump_now` 18.9 мкс, `clip_stats[:] = 0` 0.7 мкс - вместе 30 мкс), а в
том, что отдельный замер `calc_pressure` не воспроизводил чередование точных шагов и PCG.
В настоящем прогоне `calc_pressure` - **1442 мкс, 77% шага**.

### 1-2. `band_solve`: столбцы вместо строк + `fastmath` - 3.1 раза

Механизм (проход по столбцам вместо строк, `fastmath` на обратном ходе) - в `CLAUDE.md`, раздел
«Матрица давления и её решатель». Числа: 307 -> 174 мкс (столбцы, решения расходятся на 6e-16) ->
100 мкс (`fastmath`, расхождение 8e-16). `band_solve` вызывается 1 + число итераций PCG раз за шаг.
`fastmath` на `pcg_band` пробовали отдельно: 1.04 раза, не окупается, не подключен.

### 3. `p_refactor_period`: 5 -> 20

Период подбирался на 25x25. На 50x50 факторизация подорожала относительно решения (`band_chol`
растёт как `Nx^3*Ny`, `band_solve` - как `N*Nx`), и оптимум уехал вверх. Прямые замеры в цикле
оказались непригодны - разброс от фоновой нагрузки больше самого эффекта, - поэтому модель по
чистым замерам ядер: `точный путь` 2952 мкс, `band_solve` 175 мкс, итерация PCG ~195 мкс,
`стоимость(P) = (точный + (P-1) * pcg(k(P))) / P`:

| период | итераций PCG (медиана / макс) | мкс/шаг на СЛАУ |
|---:|---:|---:|
| 5 | 3 / 5 | 1070 |
| 12 | 4 / 7 | 974 |
| **20** | **4 / 8** | **~900** |
| 25 | 4 / 8 | 880 |
| 40 | 5 / 9 | 1038 |

Оптимум пологий между 12 и 40. Взято 20: внутри оптимума и с запасом 2.5 раза до `p_pcg_maxit = 20`.
Сбоев PCG на 600 шагах не было ни при одном из проверенных периодов.

### 4. Кольматация: `pow` в цикле по радиусам - 77 500 вызовов за шаг

`u_r` считала `(um * Diff_2 / r) ** (1/3)` для каждой пары (ячейка, радиус). Но `um = Um_r2*r^2`,
значит `um/r = Um_r2*r`, и корень распадается:
```
(um*Diff_2/r)^(1/3) == cbrt(Um_r2 * Diff_2) * cbrt(r)
```
`cbrt(r)` - константный массив (`cbrt_r1`), `cbrt(Um_r2*Diff_2)` считается один раз на ячейку.
Было `Nr` вызовов `pow` на ячейку, стало один. Аналогично `u_b`: `r*r*um = Um_r2 * r^4`, а массив
`r4` уже есть.

### 5. `u_c` считалась и не использовалась

`calc_velocities_h` вызывала `u_c` на каждой паре (ячейка, радиус) и передавала результат в `u_r`,
а та его не читала: ветка суффозии закомментирована. Ещё 77 500 вызовов с двумя делениями за шаг
впустую.

Сейчас `u_r` и `u_c` - живой код: суффозия перенесена из комментария под флаг `suffusion` в
`constants.py`. Флаг - константа времени компиляции, поэтому при `suffusion = False` numba выкидывает
ветку целиком, и `u_c` не вызывается: шаг тот же, результат побитово тот же. При `suffusion = True`
ветка компилируется и меняет решение (проверено прогоном на 2441 шаг). Так физика остаётся в коде и
не гниёт в комментарии, а выключенной не стоит ничего.

### 6. Обмен слоёв копировал то, что и так совпадает

`_swap_time_steps` копировал `fi`, `h_sloy`, `Ur`, `Ub` (по `Nr` элементов на ячейку) для всех
ячеек, хотя `calc_velocities_h` и `calc_qp_m_k_fi` пишут `new_*` только там, где `Wps` выше порога
кольматации. В остальных ячейках `new_*` равны текущим с прошлого активного шага, и копирование -
тождественный no-op. Проверка идёт по значению `Wps` до перезаписи в этом же проходе (сейчас
`was_clogging = Wps[i, j] > min_Wps_bound`, до присваивания новых полей). 218 -> 62 мкс при активном
парафине, побитово тот же результат.

Заодно поячеечный цикл по `Nr` заменён срезами `fi[i, j, :] = new_fi[i, j, :]` - ещё ~14%
(numba разворачивает срез в memcpy подряд лежащих элементов).

### 7. Мелочи

- `_top_bottom_heat_losses` пересчитывала `mobility_o/mobility_w`, которые `calc_mobility` уже
  положила в `lam_o`/`lam_w`;
- `mid_lam` пересчитывала теплопроводность своей ячейки на каждой из четырёх граней (заменена на
  `lam_heat` + `mid`);
- свёртка обрезаний насыщенности и подбор `dt` шли двумя проходами по одним и тем же 2500 ячейкам -
  слиты в один, `_calc_dt` теперь только про скважины (и стал вдвое короче);
- `calc_pressure` возвращала `np.ascontiguousarray(p_vec.reshape((Ny, Nx)).T)` - новый массив
  каждый шаг; теперь пишет в готовое поле развёрнутым циклом, который заодно прямо показывает
  нумерацию `idx = i + j*Nx`;
- `_check_pressure` строил bool-массив `np.all(np.isfinite(p))` каждый шаг - заменено на
  `np.isfinite(p.sum())`.

## Как мерять, чтобы не обмануться

Три ловушки, на каждую я наступил:

1. **Прогрев.** На `bench.py 30` медиана ещё содержит JIT и даёт разброс в разы. Нужно 300-400 шагов.
2. **Дрейф машины.** Последовательные прогоны «сначала все A, потом все B» дают расхождение до 10x
   при внешней нагрузке. Прогоны надо чередовать A/B/A/B и брать **минимум** медиан, а не среднее.
   И ничего не запускать параллельно с замером - два pytest фоном сдвигают все цифры.
3. **`LOGGING = True` маскирует всё.** `_logging_solution` вызывается каждый шаг (вопреки тому, что
   написано в `CLAUDE.md`) и стоит ~1000 мкс - больше половины шага: это десяток полных редукций
   `min`/`max` по полям. На его фоне разница в 40 мкс тонет и даже меняет знак. Профилировать
   `_equations_loop` надо с `LOGGING = False`.

## Где было время

### 1. Срыв векторизации цикла по граням - 50 мкс

Симптом, по которому это опознаётся: аблация показывает, что снятие **любого** из двух новых
блоков (ограничение Куранта по температуре / скрытая теплота в потоке) возвращает всю скорость
целиком, а вместе они стоят столько же, сколько каждый по отдельности. Ненадитивность - признак
того, что дело не в арифметике, а в числе живых значений: цикл перестаёт векторизоваться.

Лечится не удалением физики, а сокращением живых значений. Ключевое наблюдение: грань с оттоком
(`value < 0`) равносильна `p_c > p_ij`, то есть **вверх по потоку на ней всегда сама ячейка**.
Поэтому отток нефтяной фазы и конвективный тепловой отток - это уже считаемый `_q_out`, умноженный
на константы ячейки, и отдельных накопителей в цикле не требуют:

    fo_c = up_fraction(lo_ij, lam_ij)
    out_heat_coef = cw_ro_w * up_fraction(lw_ij, lam_ij) + Co * fo_c
    ...
    return fo_c * _q_out, out_heat_coef * _q_out + _cond

Из цикла ушли два накопителя и одна выборка вверх по потоку; осталось `_cond += lam_heat_ij`.

### 2. `lam_heat` считалась 5 раз на ячейку - 28 мкс

Своя плюс по разу на каждого из четырёх соседей, хотя величина у ячейки одна. Ровно та же история,
что с подвижностями в раунде 1: перенесена в `calc_mobility`, в поле `lam_h`. Исключение -
фиктивная ячейка за границей: там своя насыщенность из ГУ, и значение считается на месте.

### 3. Мелочи, каждая по несколько мкс

- `h_oil` пересчитывала `c_oil`, хотя вызывающая сторона уже держала её для осреднения по грани;
- `c_oil` читала `Wo`, `Wp`, `Wps` из массивов, хотя доли соседа уже лежали в локальных переменных
  (аргументы стали скалярными);
- энтальпия соседа считается только в ветке, где сосед и есть верх по потоку;
- `psi` возвращается из `temperature_equation` - ограничению Куранта по температуре нужна та же;
- ушли слои `S_0`, `m_0`, `Wo_0`, `Wp_0` и обнуление `new_*` (уравнения теперь присваивают, а не
  накапливают) - отсюда -9.7% на обмене слоёв;
- `calc_pressure` потерял 6 аргументов: правая часть больше не содержит источника по пористости.
