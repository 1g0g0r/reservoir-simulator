# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Язык

Код, комментарии, docstring'и, логи и вывод в консоль — на русском. Сохраняй этот стиль в новом коде.

## Commands

```bash
python start.py                        # запуск расчета (единственная точка входа симулятора)
python visualise_solution.py           # интерактивный plotly-отчет по последнему расчету
python create_graphs_and_animations.py # статические графики/карты в outputs/pictures (create_gif() закомментирован)
python -m paraphin                     # график начальной функции пор по размерам fi_0

python -m pytest tests -q              # или без pytest: python -m tests.test_pressure_orientation
python bench.py [шагов] [прогрев_сут]  # замер стадий шага, см. PERFORMANCE_FINDINGS.md
```

`tests/test_pressure_orientation.py` самодостаточен (строит поля в памяти, ничего не читает с диска).
`tests/test_calculation.py` сравнивает **уже посчитанный** `outputs/data/Wp={init_Wp}_processed_data.pkl` с эталоном
из `tests/test_data/` — вызов `solve()` внутри закомментирован, поэтому сначала `python start.py`, потом тест;
`init_Wp` в `constants.py` должен совпадать с именем эталонного файла (есть эталоны для 0.0 и 0.05). Сравнение идёт
по физическому времени с интерполяцией: при адаптивном шаге моменты сохранения у эталона и расчёта не совпадают.
**Эталоны сняты на сетке 20x20** — под них надо ставить `Nx, Ny = 20, 20`, иначе сравнивать нечего. Сейчас этот
тест падает (`Pressure` расходится на 11.7%) и падает так же на исходном коде: эталон устарел относительно `dev`,
его надо переснять.

`bench.py` меряет стадии шага обёртками вокруг функций `paraphin.solver`, поэтому не дублирует их длинные
списки аргументов и не отстаёт от правок сигнатур.

Установка: `uv pip install -r requirements.txt`. Python 3.10+.

`sparse-numba` в windows-колесе везёт только SuperLU (`cy_superlu_wrapper.pyd` + mingw-DLL в `vendor/`) —
уравнение давления решается им, ставить ничего не нужно. UMFPACK в колесе отсутствует как модуль, поэтому
при импорте пакет пишет `UMFPACK libraries were not found`; установка SuiteSparse это предупреждение уберёт
(проверка — просто glob по `*umfpack*.dll`), но UMFPACK не включит. Если он нужен —
`bash build_umfpack_windows.sh` (Git Bash, активированный venv): скрипт собирает `cy_umfpack_wrapper` из
исходников upstream статически против SuiteSparse/OpenBLAS из MSYS2 и кладёт в site-packages.
Статически — потому что колесо везёт msvcrt-сборки mingw-рантайма, а MSYS2 даёт ucrt: при динамической
линковке `libopenblas.dll`, `libgfortran-5.dll` и `libgcc_s_seh-1.dll` существовали бы в двух вариантах
под одним именем. Патч в `sparse_numba/__init__.py` (детект по модулю, а не по DLL) скрипт ставит сам,
но живёт он в site-packages и переустановку пакета не переживёт — тогда прогнать скрипт заново.

## Конфигурация

CLI и конфиг-файлов нет. **Всё настраивается правкой `paraphin/constants.py`**: размеры сетки (`Nx, Ny, Nr`), геометрия,
`dt`, `Time_end`, свойства флюидов, давления на скважинах, начальные условия. Скважины и ГУ задаются кодом в `start.py`
через `solver.add_well(...)` / `solver.add_bc(...)`.

`dt` из `constants.py` — только **стартовый** шаг. Дальше шаг подбирается каждую итерацию из реального
числа Куранта (`_calc_dt` в `solver.py`) и передаётся в уравнения аргументом, а не импортируется;
`CFL_target`, `dt_growth`, `dt_min`, `dt_max` лежат рядом в `constants.py`. Прежняя проверка Куранта
была нерабочей (размерность метров вместо безразмерной, номинальные вязкости, однократный расчёт при импорте).

Побочные эффекты `constants.py` на этапе импорта:
- `init_Wp`/`init_Wps` управляют всем: при `init_Wp + init_Wps ≈ 0` флаг `solver._paraphin = False` полностью отключает
  блок кольматации/суффозии (уравнения парафина, `fi`, `m`, `k` не считаются) и меняет набор сохраняемых полей;
- `init_Wp` входит в имена выходных путей (`results_path`, `Wp={init_Wp}_processed_data.pkl`).

## Архитектура

### Численная схема
IMPES на регулярной прямоугольной сетке (МКО): давление неявно (прямое решение СЛАУ), насыщенность/температура/парафин явно.

Один шаг по времени собран прямо в `Solver.upd_time_step` (`paraphin/solver.py`), а не в общей njit-обертке:
она получала скважины (jitclass) в аргументах и потому не кешировалась на диск — её компиляция стоила 5 из
9 секунд прогрева. На скорость шага это не влияет (проверено побитово на 2000 шагах).
1. `calc_mobility` — подвижности фаз `lam_o`, `lam_w`; считаются один раз и переиспользуются пунктами 2 и 5.
2. `calc_pressure` — сборка матрицы в три диагонали + `solve_band_system` (ленточный Холецкий, см. ниже).
3. `_update_wells_data` — дебиты, обводненность, КИН.
4. `_wells_loop` — дебиты в буферы источников `src_S`, `src_Wp`, `src_T`. Не пишет в поля уравнений
   напрямую: буферы заданы в тех же единицах, что и перетоки через грани (м^3/с и Вт), и попадают
   в уравнения через `cells_*_eq`, то есть делятся на поля **нового** слоя, как в постановке.
   Обнулять их не надо — скважины неподвижны, их ячейки перезаписываются каждый шаг.
5. `_equations_loop` — двойной цикл по ячейкам; порядок внутри ячейки повторяет порядок вычислений
   из постановки: кольматация (`fi` → `m`, `k`, `qp1`, `qp2`) → `flows_in_cells` → добавление
   `src_*` → насыщенность → перенос парафина → температура. `flows_in_cells` попутно заполняет
   три накопителя оттока (`cells_Q_out`, `cells_Qo_out`, `cells_T_out`).
6. `_calc_dt` — шаг для следующей итерации. Минимум по ячейкам уже посчитан в `_equations_loop`
   (три ограничения Куранта: насыщенность, перенос парафина, температура), здесь остаются только
   скважины.
7. `_swap_time_steps` — поячеечный параллельный цикл: `new_* → текущий`, вязкости от новой
   температуры. Обнулять `new_*` не нужно: уравнения пишут в них присваиванием, а не `+=`.

### Numba, а не ООП
Все горячие функции — модульные `@njit`, принимающие ~50 позиционных numpy-массивов. `Solver` — обычный Python-класс,
он только хранит массивы и раскладывает их в аргументы. Гигантские сигнатуры — намеренные, не рефакторь их в объекты:
jitclass не потянет весь набор полей.

`parallel=True` стоит там, где ячейки независимы: `_equations_loop`, `_swap_time_steps` (`solver.py`),
`_fill_matrix_and_rhs` (`equations/Pressure.py`), `calc_mobility` (`math_utils/FVM_utils.py`), `stencil_mv`
(`math_utils/band_solver.py`). Разложение Холецкого и подстановки распараллелить нельзя — рекуррентности;
`_calc_dt` и циклы по скважинам не окупают накладные расходы parfor.

**Ловушка numba в parfor:** кортеж вроде `i1, j1, hij = i, j, hij * 0.5` внутри `prange`-цикла numba приводит
к одному типу, и индексы становятся `float64`. Вне parfor такая функция компилируется, внутри — падает
на `getitem(array, Tuple(float64, int64))`. Поэтому в `flows_in_cells` свойства соседа читаются внутри
каждой ветки, а не по переприсвоенному индексу.

**Вторая ловушка — общий скратч-буфер.** `_update_fi` (`equations/Qp_m_k_fi.py`) гоняет прогонку по
`a_tdma`/`b_tdma`. Один буфер на все ячейки внутри `prange` даёт гонку: потоки затирают друг другу
коэффициенты, `fi` считается по мусору, `m` и `k` прыгают на порядки, давление вылетает за диапазон
забойных, а расчёт становится недетерминированным — два одинаковых прогона расходятся. Буферы
нарезаны по `i`: форма `(Nx, Nr)`, в цикл уходит `a_tdma[i]`. Заводишь новый поячеечный скратч —
делай так же. Проверка на гонку дешёвая: два прогона подряд обязаны совпасть побитово.

Горячие функции помечены `njit(cache=True)` — без этого компиляция занимает 25 секунд при каждом запуске.
Функции, принимающие скважины (`calc_pressure`, `_adding_wells`, `_update_wells_data`, `_wells_loop`,
`_calc_dt`, `upd_q_and_eta`), не кешируются: jitclass в аргументах, numba об этом предупреждает — сообщение
глушится в `paraphin/__init__.py`. **Важно:** numba инвалидирует кеш по mtime файла с самой функцией, а значения
из `constants.py` вшиваются в машинный код как литералы, поэтому `paraphin/__init__.py` сбрасывает кеш по хешу
`constants.py` — иначе правка `Nx` или `dt` молча считалась бы по старой сетке. Не убирай эту проверку.

Первый вызов `upd_time_step(0.0)` в `Solver.start()` — прогрев JIT; время компиляции печатается отдельно от расчета.

### Матрица давления и её решатель
Шаблон пятиточечный, неизвестная нумеруется `idx = i + j*Nx`, поэтому матрица — ленточная с полушириной `Nx`
и ровно тремя ненулевыми диагоналями. `_fill_matrix_and_rhs` (`equations/Pressure.py`) собирает их напрямую:
`diag` (центр), `ex` (связь с `idx+1`), `ey` (связь с `idx+Nx`) — сразу в положительно определённой форме
`M = -A` (диагональ положительна, внедиагональные отрицательны, правая часть с обратным знаком).
**В правой части стоят только дебиты и вклад Дирихле.** Уравнение давления получается сложением
балансов *фаз* (воды и нефтяной фазы целиком), при котором производные по времени сокращаются
полностью. Прежний источник `-((m - m_0) + m_0*S_0*(Wo - Wo_0)/Wo)/dt*volume` возникал из-за
сложения баланса воды с балансом отдельного компонента и давал невязку дебитов нагнетательной и
добывающей скважин; теперь их равенство выполняется тождественно (`tests/test_mass_balance.py`).
CSC, `sort_mask` и `data[sort_mask]` убраны вместе с прежним инвариантом «порядок записи в препроцессинге
и в сборке обязан совпадать элемент в элемент»: ячейка пишет в свои `diag[idx]`, `ex[idx]`, `ey[idx]`, и
согласовывать нечего. Скважины правят `diag[well.idx_rhs]` и `rhs[well.idx_rhs]`.
`preprocess_wells` от матрицы больше не зависит — он только раскладывает скважины и считает `idx_rhs`.

Решает `utils/math_utils/band_solver.py`: разложение Холецкого по ленте, без выбора главного элемента
(M симметрична, диагонально доминантна и неприводима, скважины и Дирихле дают строгое доминирование).
Фактор пересобирается раз в `p_refactor_period` шагов, промежуточные шаги добираются PCG с ним в роли
предобуславливателя — матрица меняется на ~0.2% за шаг. Не сошёлся за `p_pcg_maxit` — фактор пересобирается
и система решается точно, так что за результат всегда отвечает прямой метод.
На сетке 25x25 это 113 мкс против 1087 мкс у прежнего `superlu_solve_csc`; замеры всех рассмотренных
вариантов — в `PERFORMANCE_FINDINGS.md`.

Две вещи в `band_solve` выглядят странно и трогать их не надо. Прямой ход записан **столбцами**
(посчитав `y_j`, сразу вычитаем его вклад из ещё не посчитанных), а не привычной строчной суммой:
`w` имеет форму `(N, KD+1)`, и строчная форма читала бы фактор поперёк строк с шагом 408 байт — это
1.76 раза. И на нём стоит `fastmath=True`: обратный ход — редукция, без разрешения на перестановку
слагаемых LLVM её не векторизует, это ещё 1.75 раза. На `band_chol` fastmath намеренно **не** стоит:
там проверка вырожденности `w[j, 0] <= 0.0`, а fastmath разрешает считать, что NaN не бывает.
`p_refactor_period` считается от сетки — `min(40, max(5, Nx*2//5))`: факторизация растёт как `Nx^3*Ny`,
а решение как `N*Nx`, поэтому оптимум линеен по `Nx`. Коэффициент 0.4 — от замеренного на 50x50
оптимума 20, границы 5 и 40 держат PCG в пределах `p_pcg_maxit`. `sparse-numba` остался в зависимостях как независимый эталон
для `tests/test_pressure_orientation.py`, в расчёте он не используется.

Решение раскладывается в готовое поле `p` циклом `p[i, j] = p_vec[i + j*Nx]` (быстрый индекс — `i`);
раньше здесь было `np.ascontiguousarray(p_vec.reshape((Ny, Nx)).T)`, то есть новый массив каждый шаг.
Перепутать оси тут легко: без этого разворота давление зеркалится относительно главной диагонали, а на
штатной постановке (обе скважины на диагонали, однородная `k`, квадратная сетка) это незаметно — решение
симметрично. Инвариант закреплён в `tests/test_pressure_orientation.py`.

### Поля и добавление нового
Каждое динамическое поле живет двумя массивами: `X` (текущий слой) и `new_X` (новый); предыдущий слой (`X_0`) остался только у температуры. Функции уравнений
получают `(i, j, ..., dt)`, читают текущий слой и пишут в `new_*`. Добавление поля означает правку в пяти местах:
`constants.py` (init-значение) → `Solver.__init__` → списки аргументов вызовов в `upd_time_step` /
`_equations_loop` / `_swap_time_steps` → `utils/save_data_fields.py`.

Порядок внутри `_equations_loop` значим, но по другой причине, чем раньше: он повторяет порядок
вычислений из постановки задачи. `wp_equation` делит на `(m*S_o)` **нового** слоя, поэтому идёт
после `calc_qp_m_k_fi` и `saturation_equation`; `temperature_equation` идёт последним, потому что
скрытая теплота кристаллизации требует `w_p` нового слоя. Прежней ловушки «уравнение `Wp` читает
перетоки предыдущего шага» больше нет — все перетоки берутся с текущего слоя.

Обмен слоев (`_swap_time_steps`) — параллельный поячеечный цикл: `X = new_X`. Обнулять `new_*` не
нужно, уравнения пишут в них присваиванием. Слой `X_0` остался только у температуры (`T_0`) — его
читает метод Винсома-Вестервельда. Поля по радиусам пор (`fi`, `h_sloy`, `Ur`, `Ub`) копируются
только выше порога кольматации: ниже него `calc_velocities_h` и `calc_qp_m_k_fi` их не пишут, и
копия была бы тождественной. И не читай `new_X` после обмена: `save_fields` берет `m` и `k` из
текущего слоя.

Доли компонентов нефтяной фазы (`Wo`, `Wp`, `Wps`) — **объёмные**, а не массовые: замыкающее
соотношение `w_o + w_p + w_ps = 1` выполняется по объёму (как `S_w + S_o = 1` для порового
пространства), а парафин в любом состоянии имеет плотность `ro_p`. Отдельного уравнения для `Wps`
нет: решается одно уравнение переноса для суммы `w_p + w_ps` (обе формы движутся с нефтью с одной
скоростью), а разделение — алгебраическое, по пределу растворимости `_wp_saturated`. Поэтому
соотношение (4.2) выполняется точно, а не накапливает невязку.

`new_S` нигде не зажимается в `[S_min, S_max]`: границы держит сама модель — вне диапазона `f_w`
и `f_o` (`math_utils/phase_f.py`) выходят на 0 и 1, поток монотонен, и при шаге по Куранту схема
из диапазона не выносит. Прежние зажим и статистика обрезаний (`clip_field`/`clip_stats`) убраны.

### Скважины
`WellStruct` — numba `jitclass` (`utils/well.py`), скважины лежат в обычном списке (`preprocess_wells`).
Формула Писмана записана как `q = 2*pi*k*h/ln(r_e/r_w) * (f/mu) * (P_забой - P_ячейки)`, то есть
**`q > 0` — закачка, `q < 0` — отбор**, как у источников в уравнениях баланса. Проницаемость берётся
текущая (`k` ячейки): кольматация призабойной зоны — основной эффект задачи. Скважины неявны по
давлению: слагаемое с `P_ячейки` уходит на диагональ, с `P_забой` — в правую часть. Без этого
задача с непроницаемыми границами чисто нейманнова, матрица вырождена, и решение существует лишь
при нулевой сумме дебитов.
Критерий останова (`wells[self._producer].eta >= max_eta`) и условие сохранения читают обводненность
добывающей скважины, поэтому она должна быть **ровно одна**; её индекс `Solver.initialize` находит сам
по `is_injector` и кладёт в `_producer`, порядок вызовов `add_well` не важен. Число нагнетательных
не ограничено — остальные циклы идут по всем скважинам. Нет добывающей или их несколько — `initialize`
падает с внятным сообщением, а не по IndexError где-то в цикле.

### Граничные условия
Массив `boundary_conditions[bound, field, (тип, значение)]`, индексы — из enum'ов `Bound` / `DataField` / `TypeBC`.
`get_bound` возвращает значения enum'а напрямую: `j` за сеткой — это Left/Right, `i` за сеткой — Top/Bottom.
Отсутствие явного ГУ = Нейман с нулевым значением (непроницаемая граница). `get_bound(i, j)` определяет границу
по вылету индекса за сетку, `apply_bc` возвращает значение поля в фиктивной ячейке.

### Логирование
Полный лог (`_logging_solution`) пишется по тому же расписанию, что и сохранение полей (`sol_time_step`),
и обязательно **до** `_swap_time_steps` — тот обнуляет `new_*` поля, которые логируются. Каждый шаг логировать
нельзя: `psutil.virtual_memory()` на Windows стоит 3.5 мс, больше чем весь остальной шаг, поэтому
`_logging_resources` перешёл на память процесса.

### Вывод результатов
`save_fields` дозаписывает очередной слой (шаг сохранения — `sol_time_step`) в **один** открытый файл
`outputs/results_wp={init_Wp}/layers.pkl`; хендл живёт в `Solver._layers_file` и открывается при первом сохранении.
В `finally` блока `Solver.start()` файл закрывается, `convert_pkl_files(self._i_img)` склеивает слои в
`outputs/data/Wp={init_Wp}_processed_data.pkl` (формат `[n_layers, data]`, у каждого поля ведущая ось — время),
после чего `rmtree(results_path)` **удаляет промежуточный файл**. Это происходит и при `KeyboardInterrupt`.

Один файл вместо файла на слой: на 794 сохранениях запись стоит 0.06 с вместо 0.67, склейка — 0.06 с вместо 1.92,
и из склейки ушли разбор времени из имени файла, сортировка и параллельное чтение. Память не растёт: `dump`
отдаёт байты в ОС и слои не копит (замер: +4 МБ на сетке 100x100 независимо от их числа). А вот сама склейка
держит все слои разом — на 100x100 с парафином это 2.7 ГБ, и это единственное место выгрузки, которое упрётся
в память на больших сетках.

Поле `fi` выгружается **одной кривой по радиусам** из точки `save_data_fields.FI_PROBE`, а не полем
`(Nx, Ny, Nr)`: обе визуализации строят `Scatter(x=r, y=...)`, то есть ждут вектор длины `Nr`. Полное поле
весило 75% слоя — на нём и упиралась в память склейка.

`convert_pkl_files` берёт число слоёв аргументом от `Solver`; без аргумента считает их проходом по файлу — так её
зовёт `visualize_solution`. Живёт он в `paraphin/utils/read_data_files.py` — пара к `save_data_fields.py`, а не
в `visualisation_utils`: пока он лежал там, импорт склейки тянул в расчёт matplotlib и plotly. Оборванная последняя запись склейку не ломает: массивы обрезаются до фактически
прочитанного. Формы массивов выводятся из первого слоя, а не задаются по имени поля.
Возобновления расчета с последнего слоя нет (пункт бэклога в `TODO_list.txt`). Вся папка `outputs/` в `.gitignore`.


## Что где лежит

Расчёт **не импортирует** визуализацию: `paraphin/utils/__init__.py` намеренно не ре-экспортирует
`visualisation_utils` (тот тянет matplotlib, plotly, PIL, joblib — полсекунды импорта). Точки входа
(`visualise_solution.py`, `create_graphs_and_animations.py`) берут её напрямую. Не возвращай этот импорт.

Геометрия граней ячейки (`DI`, `DJ`, `HIJ`, `AREA`) лежит в `utils/math_utils/FVM_utils.py` — одна копия
на сборку матрицы давления и на расчёт перетоков. Производные от сетки радиусов (`r1..r6`, `cbrt_r1`,
`r_pass`, `n_pass`) — в `paraphin/__init__.py`.

Скорости потери порового объёма разделены на два поля: `qp1` — осаждение на стенках пор (изымается
чистый парафин), `qp2` — блокирование каналов (из фильтрации выводится весь объём канала вместе с
нефтью, поэтому в уравнении парафина этот сток идёт с множителем `w_p + w_ps`). Их сумма
нормируется на фактическую убыль пористости, `(qp1 + qp2)*dt = m - m_new`; тождество закреплено в
`tests/test_mass_balance.py` и на него опираются и насыщенность, и баланс парафина. Поле `Ub`
хранит **коэффициент** `b(r)`, а не саму скорость блокирования `ub = b(r)*fi`: разделение нужно,
чтобы взять слагаемое блокирования неявно в `_update_fi` — при явной записи большое `b*dt` уводит
`fi` в минус, и безусловная устойчивость прогонки положительности не гарантирует.

Режим кольматации выбирается по `r_pass = D/(2γ)` — радиусу, при котором частица проходит горло
капилляра: уже — затыкает целиком (`Ub`), шире — оседает на стенке и сужает (`Ur < 0`). Сужение
во времени схема отражает не изменением `r` (сетка `r1` фиксирована), а переносом `fi` по оси
радиусов в `_update_fi`, так что капилляр сам переходит между режимами, сползая по сетке.

Потери тепла в кровлю и подошву — `equations/Temperature.py`, метод выбирает флаг
`heat_losses` в `constants.py` (тоже константа уровня модуля, ветка сворачивается на
компиляции). `2` — схема Ловерье: обмен `Θ = -2·K_ff·dT/dz` в приближении ступеньки,
`2·K_ff·(T-init_T)/(h·√(π·α_ff·t))`, без состояния. `True` — Винсом-Вестервельд (TOUGH2 User's
Guide §7.4, статья в `resources/литература/неизотермическое/`): пробный профиль температуры в
породах, одно поле состояния `Solver.E_ff` (накопленный интеграл перегрева, обновляется на месте
внутри `prange`). Оба варианта закреплены в `tests/test_heat_losses.py`, там же
аналитическое решение Ловерье как эталон. 

Суффозия (вынос осевших частиц потоком) — второе слагаемое в `u_r`, под флагом `suffusion` в
`constants.py`. Флаг **должен оставаться константой уровня модуля**: numba сворачивает `if suffusion:`
на этапе компиляции, поэтому выключенная ветка не стоит ничего — ни `u_c`, ни `um` не считаются.
Сделаешь его аргументом или полем — вернёшь `Nx*Ny*Nr` лишних вызовов `u_c` за шаг.
`h_sloy` нужен только этой ветке: он копит `-Ur*dt`, то есть ту же толщину осадка, которую адвекция
`fi` уже отражает сползанием по оси `r`. Включая суффозию, реши, что считать текущим просветом —
`r1[ij]` или `r1[ij] - h_sloy`, — иначе два учёта разойдутся.

Общее описание полей-аргументов уравнений — в докстринге пакета `paraphin/equations/__init__.py`,
один раз на все функции; в самих функциях остаётся только специфичное.
